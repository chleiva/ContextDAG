## 1. What the handoff asks for, in one paragraph

F0 handed the oracle the exact gold parent set. F0.5 asks whether a *cheap, non-LLM candidate
generator* (branch heads, recent turns, embedding neighbours, entity overlap) puts that gold set
inside a bounded candidate pool (Candidate Recall@k), and, where it does, whether an oracle that
may only pick from that pool keeps most of F0's advantage over full history. Before that, the
judge must be switched from Opus 4.6 (70% of F0's spend) to a cheap cross-vendor model, and the
switch must be validated on a calibration subsample against Opus's existing verdicts. Hard cost
limit $25, warning at $18. Output is `F0.5_RESULTS.md` with a mechanical PASS / PIVOT.

## 3. Other things found during reconnaissance that shape the plan

1. **`F0_Analysis_and_Recommendations.md` is not in the repo.** The handoff cites it in five
   places (compound_turn split evidence, check-3 early signal, contribution framing). Not
   blocking; if the user has it, adding it to the repo root lets the report cite it properly.
2. **spaCy is not installed** in `.venv`. Plan adds `spacy` + `en_core_web_sm` (~50 MB, local,
   free) as a `f05` optional dependency group in `pyproject.toml`.
3. **Non-Anthropic models need a second client.** F0's `llm.complete` uses the Anthropic SDK's
   `AnthropicBedrock`, which only serves Anthropic ids. F0.5 adds a `converse`-based backend
   (boto3, already installed) behind the same `complete()` signature, same retry/backoff, same
   ledger recording, plus `reasoningContent` stripping for thinking models.
4. **The pool cap k rarely binds on this benchmark.** Scenario histories are short: 10 of 13
   families have 5–12 prior turns. The cap binds (history > k) on:

   | k | scenarios where cap binds | families |
   |---|---|---|
   | 3 | 145 / 145 | all |
   | 5 | 117 / 145 (81%) | all |
   | 10 | 36 / 145 (25%) | constraint_retention, knowledge_update, long_noisy_side_thread, three_way_join |
   | **15 (handoff primary)** | **34 / 145 (23%)** | constraint_retention, knowledge_update, long_noisy_side_thread |
   | 20 | 29 / 145 (20%) | same three |

   At k=15 the pool can hold the whole history for 111 scenarios, so strict Recall@15 is
   guaranteed 1.0 there and the 0.85 gate is only tested by 34 long scenarios. This is a property
   of benchmark 1.1, not a flaw in the handoff, but the report must say it plainly. See
   DECISION 3 for how I propose to handle it.
5. **Advantage-retention is a fragile ratio.** On benchmark 1.1, F0's oracle-DAG advantage over
   full history is +2.65 pp (Sonnet) and +2.61 pp (Haiku), with bootstrap CIs spanning zero.
   "Retain ≥80%" therefore means "candidate oracle beats full history by ≥2.1 pp", a bar that a
   1 pp judge wobble flips either way. See DECISION 4.
6. **Mixing judges would contaminate the retention number.** F0's full_history and oracle_dag
   scores are Opus verdicts; the candidate-oracle arm would be cheap-judge verdicts. I propose
   re-judging F0's existing full_history and oracle_dag answers (2 methods × 2 models × 145 =
   580 instances, ≈ $1 with DeepSeek) with the adopted judge so every arm in the retention and
   non-inferiority comparisons shares one judge. F0's Opus numbers remain the published F0 result.
7. **`new_root` has an empty gold set** (8 scenarios). Recall is vacuously 1.0. I will report
   recall both including and excluding `new_root`; the gate uses the handoff's "all 145" mean,
   which I will state alongside the 137-scenario figure.

Every stage is idempotent and keyed like F0 (`scenario_id|method|budget|model`); a crash resumes
where it stopped. Every LLM call goes through `complete()` and is ledgered before and after.

### 4.2 Candidate generator (handoff §2.2–2.3), per scenario, query = last turn

Structure of *prior* turns is taken from their gold parents (assumes earlier routing was
correct; stated as an assumption in the report). Primary parent = `gold_parents[0]`.

1. **Active branch**: walk back from the immediately preceding turn along primary parents,
   depth ≤ 3.
2. **Inactive branch heads**: every prior turn that is nobody's primary parent, other than the
   preceding turn.
3. **Semantic top-10**: all-mpnet-base-v2 cosine between the query user message and each prior
   turn (user + assistant text). F0's cache stores only selections, so vectors are recomputed
   once (~2 min CPU) and cached to `results/raw/embeddings.npz`.
4. **Entity / identifier overlap**: spaCy `en_core_web_sm` entities (PERSON, ORG, GPE, LOC,
   PRODUCT, EVENT, WORK_OF_ART, LAW, DATE, MONEY, QUANTITY, CARDINAL...) lower-cased, plus regex
   for backtick spans, double-quoted phrases, and snake_case / CamelCase identifiers. A prior
   turn qualifies if it shares ≥1 extracted item with the query. Stop-list of generic words.
5. **Recency safety net**: last 5 turns.

Union, dedup, record per turn: sources hit, cosine, recency rank. Cap to k by (number of
sources desc, cosine desc, recency desc). k sweep: {3, 5, 10, 15, 20, uncapped}. Also record
pool size / history size, and per-source ablation recall (drop one source at a time), which is
what §6 of the report template needs to say which heuristic under-performs.

Sanity check by hand on 8 scenarios (two_branch_join, three_way_join, resume,
long_noisy_side_thread, knowledge_update, constraint_retention, compound_turn ×2) before
anything is billed.

### 4.3 Judge calibration (handoff §1.3)

- Sample from F0's 2,610 already-judged instances, seed 20260913, stratified: families
  proportional, models 50/50, methods spread over full_history, sliding_window@1024,
  semantic_retrieval@1024, oracle_tree, oracle_dag.
- **DECISION 2 — sample size.** Handoff says 80. With three cheap candidates the whole pass costs
  ≈ $0.70 at 160 instances (≈ 640 checklist items), which roughly halves the kappa CI width.
  I recommend 160; 80 is the handoff-faithful choice.
- Opus reference = F0's existing scores (no new Opus calls). Same judge prompt verbatim, including
  the fallback variant for non-JSON output.
- Metrics per candidate judge: item-level Cohen's kappa (pooled, and per family and per model),
  raw agreement, per-instance |Δ checklist score| (mean and 90th pct), leakage kappa, method
  ranking by mean score vs Opus's ranking on the same subsample (Spearman plus the exact-order
  check), cost per call as actually ledgered.
- Adoption bar (frozen): mean item kappa ≥ 0.6, mean |Δ| ≤ 0.05, method ranking preserved.
  Ranking rule detail I propose: methods whose Opus means differ by less than 0.03 on the
  subsample count as a tie and may swap; everything else must keep order.
- **STOP AND CHECK IN #2** with the calibration table and the recommended judge (handoff §5.2).

### 4.4 Candidate-realistic oracle and re-measurement (handoff §2.5)

New method `candidate_oracle` with budget label k. Selected = gold ancestor closure ∩ pool_k.
If the closure is not a subset of pool_k → fail-open to full history, record
`recall_fallback=true`. Primary k=15; k=5 and k=10 also run as sensitivity for the answer
arm **only if** recall differs from k=15 (otherwise the contexts are identical and nothing new
is learned; identical contexts are copied, not re-billed).

Answers: Sonnet 4.6 and Haiku 4.5 on all 145 (290 calls). Re-measure everything F0 measured:
tokens, precision/recall/F1/sufficiency, irrelevant ratio, checklist score, leakage.
Two views reported: "all instances incl. fallbacks" (deployed-system view) and "recall-holds only".

**DECISION 5 — MiniMax M2.5 exploratory arm (§1.6).** Recommended: option (a), keep A/B and add
M2.5 as arm C. For arm C to mean anything it needs its own baselines, so run M2.5 on
full_history, oracle_dag and candidate_oracle@15 (435 calls, ≈ $1–1.5 at the budgeted upper
rate). Option (b) (replace Haiku) is available but forfeits F0 comparability for B.

### 4.5 Judging and analysis

- Adopted judge scores all new answers (290 + 435) plus the 580 F0 full_history/oracle_dag
  re-judge (§3.6). Prompt identical to F0's.
- Paired bootstrap, 10,000 resamples, per model: candidate_oracle vs oracle_dag, candidate_oracle
  vs full_history, on checklist score and tokens. Recall@k with bootstrap CIs by family, pooled,
  and compound_turn split by variant (variant read from `evidence_spans` / builder notes).
- Pareto plot overlaying F0's nine methods with candidate_oracle@{5,10,15}.
- Decision applied mechanically; report per §6 template plus a candidate-source breakdown.

## 5. Thresholds to freeze (handoff §3; DECISIONS 3 and 4)

```yaml
f05_decision_thresholds:
  primary_k: 15
  min_candidate_recall_at_k: 0.85        # strict, mean over all 145 scenarios at k=15  (handoff)
  min_advantage_retention_pct: 80        # (handoff) — see DECISION 4
  judge_calibration_min_kappa: 0.6
  judge_calibration_max_score_delta: 0.05
  judge_ranking_tie_band: 0.03           # proposed addition, §4.3
```

**DECISION 3 — the k=15 gate is near-vacuous on 111 short scenarios.** Options:
  (a) Keep k=15 as the sole gate exactly as the handoff wrote it, and report k=5 and the
      per-family long-scenario recall as prominent secondary results (handoff-faithful, least
      goal-post movement). **Recommended.**
  (b) Add a second pre-registered gate: strict Recall@5 ≥ 0.85, so the cap is tested on 81% of
      scenarios. Stricter and more informative, but it is a new bar invented today.
  Either way the report states the binding statistics from §3.4.

**DECISION 4 — retention metric.** Options:
  (a) Handoff as written: retention = (cand − full) / (dag − full) ≥ 80%, all three arms judged
      by the adopted cheap judge (per §3.6). Simple, but fragile for the reason in §3.5.
  (b) Replace with F0's own non-inferiority pair: candidate_oracle vs full_history ≥ −5 pp at the
      bootstrap CI lower bound is *not* required, point estimate within −5 pp, **and** token
      reduction ≥ 40% versus full history (with fallbacks included). Retention % still reported.
      **Recommended**: it reuses F0's pre-registered logic and is robust to a 2.6 pp denominator.
  (c) Both must hold.
