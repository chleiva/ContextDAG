## Where the project actually stands

**Phase F0 (oracle feasibility): complete, passed.** Unchanged from before — see prior version of this doc or `claude/F0_RESULTS.md` / `claude/F0_Analysis_and_Recommendations.md`.

**Phase F0.5 (candidate-realism check): complete, passed.** Run 14 September in a separate session per its handoff. Headline: a cheap, non-LLM candidate generator (branch-chain + inactive heads + embedding top-k + entity overlap + recency) puts the full gold-parent closure inside a 15-turn pool on 99.3% of scenarios; an oracle restricted to that pool keeps F0's ~69% token reduction with checklist quality within the non-inferiority margin (+3.0pp Sonnet, +3.1pp Haiku vs. full history). Exploratory MiniMax M2.5 arm (added, not substituted, per the prior session's decision) beat Haiku 4.5 on every method. Full numbers: `claude/F0.5_RESULTS.md`. Independent critical review, which is the operative document for what to do next: `claude/F0.5_Analysis_and_Recommendations.md`.

**The review's bottom line, which matters more than the RESULTS.md headline:** the PASS is procedurally clean and stands, but it was measured on an instrument too weak to be a real stress test — benchmark 1.1's histories average ~9 turns, so at k=15 the "candidate pool" holds 89% of the entire conversation on average. Recall can't fail on a filter that barely filters. The review does not overturn the verdict but reframes what it license and elevates one item (benchmark 1.2) from a nice-to-have to blocking.

**Check 3 (retrieval/compression comparability): complete, run 14–15 September as an analysis pass on benchmark 1.1 (`check3-handoof.md`; results `claude/CHECK3_RESULTS.md`; thresholds frozen in `f05-candidate-realism/manifest.yaml` → `check3` at commit d4204fb before any computation; confirmatory-with-disclosure).** Under the primary judge (Opus 4.6 verdicts already on disk, zero new Opus calls) `candidate_oracle@15` is non-inferior (margin −0.03, cluster bootstrap over the 145 scenarios, Holm over the four comparisons) to `semantic_retrieval@{1024,2048}` and `rolling_summary@{1024,2048}` for both Sonnet and Haiku, at 0.38–0.53× their context tokens: **PASS for both response models.** Point estimates favour the reference on all eight comparisons; only Sonnet vs `rolling_summary@2048` has a CI excluding zero, so this is a non-inferiority-plus-token-ratio result, not a powered superiority claim (≈520 scenarios would be needed). Where structure separates regardless of the quality verdict: precision 0.95 vs 0.43–0.49, leakage 1–4% vs 15–19%. Verification: candidate-oracle and oracle-DAG prompts are byte-identical on all 432 same-turn-set pairs (no order effect); only 23/432 identical prompts gave identical answers (Bedrock temperature 0 is not deterministic, which is the noise-floor mechanism); the 32 off-route Opus calls were all in the MiniMax arm. **Benchmark 1.2 Stage A length pilot: complete, verdict FLAT, run 15–16 September (`claude/BENCHMARK_1.2_PILOT_RESULTS.md`; scenarios tagged `1.2-pilot`; gate frozen at 863788c before the first billed call).** 39 of 40 long scenarios generated (30–60 turns, ≈6,600 full-history tokens, closure ratio median ≈0.15), Sonnet 4.6 as writer (user's choice B), four arms × Sonnet/Haiku/MiniMax, Llama-judged, $23.55. Cosine gate: final set 100%, but **first-attempt pass rate 48%** (the writer produces separable filler unprompted; the gate-with-feedback loop is what made distractors close); the pipeline stopped there as planned and was continued on the user's finish instruction, disclosed in the report. **Primary result: `oracle_dag − full_history` = −0.375 (Sonnet), −0.069 (Haiku), −0.033 (MiniMax): FLAT, and negative.** The mechanism is not missing context but **retraction**: given only the gold turns, Sonnet 4.6 disowns the earlier assistant messages as fabrications in 51% of oracle-DAG answers (Haiku 28%, MiniMax 0%; 5% on full history), because the writer put 80% of gold-turn text into *assistant* messages (72% in 1.1) and a pruned context shows an assistant asserting facts no visible user message supplied. Excluding retraction scenarios the contrast is still ≤ 0: at 6.6k tokens all three responders use full history without difficulty (0.81–0.95), so there is no headroom for structure to recover at this length. The efficiency claim holds (0.13× tokens, precision 1.0 vs 0.13, leakage lower). **Consequences:** (1) the length hypothesis behind Stage B is not supported at 30–60 turns; per the FLAT branch, benchmark 1.2 becomes ≈60–80 long scenarios for the efficiency/leakage claims and the paper is an efficiency-and-leakage paper unless a much longer regime (100+ turns, >20k tokens) is tested; (2) **a grounding rule for every generator, 1.1 included: gold facts must be introduced by the user or cite a user-supplied source, never asserted by the assistant alone**, or any pruned context, including a router's, will trigger fabrication-retraction in Anthropic responders; (3) the retraction behaviour itself is a router-design requirement (context must carry provenance) and a publishable observation. Generator engineering cost $4.96 of waste before three defects were fixed mid-run (recorded in the report §8).

## What to do next

**Build benchmark 1.2 before running check 3.** 30–60 turn histories, concentrated in the join, resume, and `long_noisy_side_thread` families (plus growing `compound_turn`'s first-request arm past n=5 and `three_way_join` past n=8). This is now the single highest-leverage item on the project — not because F0.5 failed, but because check 3 (retrieval/compression comparability) run on benchmark 1.1 would inherit the same "no k is both a filter and high-recall" degeneracy, in exactly the comparison most likely to decide the paper's contribution claim (semantic retrieval already looked competitive with oracle DAG in F0's own data). Full reasoning: `F0.5_Analysis_and_Recommendations.md` §4, §10.1.

**Scope, but do not yet build, one router component:** an insufficiency detector (spec §7.5's "expand context on low confidence"). **Still not started, deliberately:** the automatic router and the Context Explorer UI.
